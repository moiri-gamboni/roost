# scheduled/ — cron and timer jobs

Deployed to `~/roost/claude/scheduled/`; triggered by `files/cron-roost` unless noted. Every job logs to journald as `roost/<script>` and notifies via ntfy through `_hook-env.sh`. Headers with the full policy: `agents-cleanup.sh`, `btrfs-balance.sh`, `session-daily-brief.sh`, `vision-abuse-watch.sh`, `track-ssh-activity.sh`.

- `health-check.sh` — every 5 min. Checks Caddy, ntfy, Tailscale, cloudflared, earlyoom (service up, plus every `sending SIG…` line of its journal since the last run replayed as a high-priority ntfy, window kept in `$HOOK_RUNTIME_DIR/earlyoom-since` so a delayed run misses no kill), disk, and btrfs **unallocated** space on both filesystems (`df %` misses this: unallocated=0 with a full metadata pool is what force-flips the fs read-only, seen 2026-08-19 at df=75%). Below 5GiB it runs `btrfs-balance.sh` itself (cooldown `btrfs-balance-auto`, 24h, under the cron line's flock) and alerts only if still low afterwards, saying whether the balance ran and what it changed; a balance that relocates nothing means the chunks are full of extents snapshots still pin, so it then prunes the oldest *timeline* snapshots of that filesystem's snapper config (three per hour, cooldown `btrfs-prune-<config>`; never `number`/important ones or the off-site backup's pinned parent, whose cleanup algorithm is empty), balances again — a deleted snapshot only frees extents inside chunks — and reports what it pruned and where unallocated ended up (`btrfs headroom restored` at default priority when that fixed it). Hard failures bundle into a high-priority `Service health alert`, cooled down by failure-set hash (notify on set change, else at most hourly). The disk check alerts on trend rather than level: above 90% it always reports, and between 80 and 90 only once usage climbs 3 points past the level last reported (baseline in `$HOOK_RUNTIME_DIR/disk-alert-pct`, tracked back down as usage recovers), so a disk parked high stays quiet while a real climb still pages. Soft signals send their own ntfy: memory headroom (`MemAvailable` + free swap as a share of RAM + swap, so it follows the swap file's size) at high priority once it drops under 20%, then only every further 5 points down, baseline `$HOOK_RUNTIME_DIR/mem-alert-pct` cleared at 25% so a value hovering at the line does not flap — swap *used* is deliberately not the signal: with swappiness 10 the idle pages of long-lived sessions sit in swap for days with most of RAM available and no stall; memory thrash, PSI `full avg300` ≥ 10% (the share of the last five minutes every runnable task spent stalled on memory, the kernel's own measure), high priority, 1h cooldown; pending reboot via `/var/run/reboot-required` (default priority, 7-day reminder, re-arms on a new mtime). Sources `health-check-apps.sh` (from `files/travel/travel-health.sh`) and then `private/health-check-apps-private.sh` if present, which sources `health-check-attention-queue.sh`, the attention queue's dead-man (Beeper Server answers, every account connected, the pass's stamp under 45 min with no alarm, units active and enabled, egress policy intact in both families with a two-sided probe and one self-heal, kernel-journal rejects to anything but the telemetry hosts; tested by `files/private/tests/attention-queue-health.sh`).
- `auto-update.sh` — daily at 2:50am, a start chosen so the ~4-minute run, cleanup included, ends before snapper's 3:00 hourly snapshot: what the cleanup removes is never pinned by a fresh snapshot (started on the hour it would be, for 24 h). ntfy summary only when something updated or failed or a major version is waiting; a no-change run is silent. No snapshot of its own (snapper's hourly timeline is the rollback; a pinned per-run snapshot would hold the very junk the cleanup reclaims). Safeguards: 7-day release cooldown, major-version guard (blocked and reported). Covers Claude Code, Codex CLI, claude-code-tools, aichat-search, claude-code-transcripts, Go, fnm, Node.js LTS (which strands plain `npm i -g` globals, hence `--prefix "$HOME/.local"` in the global CLAUDE.md), uv, gitleaks, dufs, rclone (pinned selfupdate), PrivateBin, acme.sh, agent-browser (via `npm i -g --prefix "$HOME/.local"`, never its own `upgrade`, which would land in the fnm-versioned global; then `agent-browser install` for the Chrome build the new CLI expects), OS packages. Xray-core is deliberately not here (a restart would hit the in-country user at peak time; it updates on `./deploy.sh` re-runs). Ends by running `disk-cleanup.sh` as a subprocess (sourcing would cut the run short on its `exit 0`) and folding its stdout summary into the update ntfy.
- `disk-cleanup.sh` — reclaims regenerable artifacts; runs last inside `auto-update.sh`, so it sees that run's leavings (the Node version the LTS bump just superseded, the Claude Code version `claude update` replaced, the apt archives). `--dry-run` prints the plan and deletes nothing. Removes: superseded fnm Node versions, VS Code Remote server builds, Claude Code versions beyond the newest two, pipenv virtualenvs whose `.project` names a directory that is gone, package-manager caches, dangling Docker layers, the engine's build cache (`--builder default`, because plain `buildx prune` only reaches the current builder), leaked buildx builders (not current, container over a day old: the aws_infra deploy scripts create one per deploy and never remove it, ~1 GB each on the data volume), journal above 800M. Three guards keep a Node version alive — it is fnm's `default`, a `.nvmrc`/`.node-version` pins it, or it hosts a global CLI (fnm keeps globals per version, so deleting it uninstalls the tool; these are reported so the tool can be reinstalled with `--prefix "$HOME/.local"`). It also re-anchors dangling `~/bin` corepack shims (`pnpm`/`pnpx`/`yarn`/`yarnpkg`) to fnm's `default` alias rather than a version directory. Never touches the runtime browser caches — `~/.agent-browser/browsers` (agent-browser's Chrome for Testing), `~/.cache/ms-playwright` (roughdraft, podcast-studio) and `~/.cache/puppeteer` (mmdc) — nor repos, worktrees, `drop/` or transcripts. `uv cache prune` is skipped rather than forced when a live `uv`/`uvx` process holds the cache lock, which any session's serena MCP server does.
- `btrfs-balance.sh` — Sunday 2:30am, and on demand from `health-check.sh` when unallocated drops below 5GiB. `/` + `/mnt/roost-data`: `-dusage=50 -dlimit=30` data-chunk balance returning slack to the unallocated pool so metadata can keep growing. Data chunks only, never metadata. Logs before/after unallocated. A higher `-dusage` is not an escalation path: measured 2026-08-31 on chunks averaging 92% full, `-dusage=90` relocated 15 chunks and *lost* 0.3GiB of unallocated to the metadata chunk the relocation itself needed.
- `agents-cleanup.sh` — daily 3:30am. Removes `$CLAUDE_CONFIG_DIR/jobs/<id>/` for terminal-state, idle, pid-dead agent sessions idle ≥48 weekday hours, only when the connection-activity marker is ≤24h old (so vacation days don't churn the list). Transcripts, worktrees and branches untouched; sessions stay `--resume`-able. `--dry-run`, `--marker FILE`; env `AGENTS_CLEANUP_IDLE_HOURS`, `AGENTS_CLEANUP_ACTIVITY_HOURS`.
- `track-ssh-activity.sh` — every minute; touches `~/roost/claude/last-connection-activity` if `ss` shows an SSH (22) or ET (2022) connection. The marker agents-cleanup gates on.
- `ram-monitor.sh` — systemd timer, every 30s, journal only (`journalctl -t roost/ram-monitor`): a big process is routine, a kill is what pages, and health-check's earlyoom replay sends that; these lines are the record of what was big beforehand. Any process >3GB RSS (logged PIDs tracked to avoid repeats, logged again after 512MB of growth), and the processes sharing one command name >6GB together (logged names tracked in `ram-monitor-groups` until the group drops under the line, logged again after 1GB of growth) — the shape of the 2026-09-20 hang, five ripgreps under the per-process line. Sourcing the script defines its functions only; `tests/ram-monitor.sh` drives them on fixture `ps` output.
- `vision-abuse-watch.sh` — daily; ntfys never-seen source IPs on the Path D inbound (`/var/lib/roost-travel/vision-seen-ips.txt`).
- `session-daily-brief.sh` — daily 06:40: sonnet-summarized brief of yesterday's sessions, active/attended time, per-session usage (day-sliced est % of the weekly cap + share of the day's tracked burn, grouped per login when several appear, never summed across logins; $ never shown) and commits; ntfy plain text + archive under `usage/briefs/`.
- `roughdraft-watch.sh` — daily 07:10. The global `roughdraft` is built from our fork (global CLAUDE.md, Roughdraft section), so this watches upstream `main`, the npm version and the state of the PRs we carry, and ntfys only on change, saying what it implies for the next rebase. Signature-diffed against `claude/state/roughdraft-watch.state` (one `key=value` per line, matched whole-line so `npm=0.1.1` can't match inside `npm=0.1.10`); a missing state file seeds silently. Needs `gh` authenticated and says so via ntfy if not.
- `scheduled-task.sh` / `run-scheduled-task.sh` — run Claude Code tasks as headless `claude -p` in tmux windows of a `cron` session. No task is currently active (a weekly memory-cleanup task is defined but disabled in `cron-roost`).
