# scripts/ — user CLIs

Deployed to `~/roost/claude/scripts/` and symlinked into `~/bin`. `roost-apply.sh` (config deployment; usage in the root CLAUDE.md), `roost-net.sh` (travel VPN; `files/travel/CLAUDE.md`) and `agent-worktree.sh` (composite session worktrees, and `isolate`, one repo's worktree taken on demand by a running session; its header carries the full contract, `tests/agent-worktree.sh` the behavior spec — two facts it builds on: Claude Code removes a *clean* hook-created worktree itself on exit and never calls WorktreeRemove for git worktrees, and SessionEnd fires *after* that removal with cwd back at the launch repo, which is why sub-repo worktrees live outside the root in `<name>.repos/` and are only symlinked in; an `isolate` record has no root at all, so finish integrates it straight away) are documented elsewhere.

## `conflict-watch` — who is writing where

`conflict-watch.py` (`~/bin/conflict-watch`) is both the root daemon (`conflict-watch run`, `conflict-watch.service`) and the CLI the hook and the sessions call; its docstring is the contract, `files/conflict-watch.conf` the unit rules (first match wins, relative to `~/roost`; edit that file when the workspace layout changes, then restart the service). Mechanism:

- **Seeing writes.** One fanotify group (`FAN_CLASS_NOTIF`, never a permission class: a dead or stuck daemon must not block a write) with a `FAN_CLOSE_WRITE` mount mark on the mount holding `~/roost` (the btrfs root; the mirrors under `apart-research/mirrors/` are separate mounts and out of scope anyway). Event paths outside `~/roost` are dropped before any other work. A watched write is credited at once (its writer may exit any moment) but named 0.2 s later through the event's fd, which follows a rename: Edit/Write, editors and `sed -i` write a temp file and rename it over the target right after closing it, and the name at event time would be the temp one (`a.py.tmp.<pid>.<hex>`), which the git check could never match against `git status`. Deletes and renames are invisible: the dirent events are refused on a mount mark (EINVAL) and a filesystem mark on a btrfs subvolume (EXDEV), probed 2026-09-24, so `rm`/`mv` in a held unit are only caught by the hook's Bash check.
- **Crediting a write to a session.** The writer pid's parent chain is walked to the *outermost* pid in the Claude Code registry (`sessions/<pid>.json`, open = pid alive with the recorded `procStart`): the claude process itself for Edit/Write, its Bash children and anything they start otherwise, and a `claude -p` helper counts as its parent. The proc connector (netlink `CN_IDX_PROC`) supplies fork parents for writers that exit before their event is read — `sed -i` is usually reaped by then (2.8% of a probe's writes without it, 0 of 600 with it; 103 of 300 short-lived writers in `tests/conflict-watch-daemon.sh` needed it). The connector is drained before every fanotify batch, since a writer's fork is queued before its write. `CLAUDE_CODE_SESSION_ID` in the writer's environment (Claude Code sets it on the Bash tool's shell) catches detached processes that predate the daemon. Nothing found = not a session (cron, the mirrors, the user's own shell): the write holds nothing. `skip-writer` rules drop tools that rewrite many units on a session's behalf (`tasks pull`); `skip-name` drops `.git/`, caches and similar; and a repo hold counts only through a file git does not ignore (`git check-ignore`, run as the user, never as root).
- **Holds.** unit → session → {since, last write, the files}. A hold lasts while the session is open (pruned every 5 s), until a release (`conflict-watch release`, which drops a request in `requests/` for the daemon), and survives a daemon restart (`state.json` in the runtime dir, kept by `RuntimeDirectoryPreserve=restart`); it cannot survive a reboot, and neither can the sessions.
- **Notices.** A write into a unit another open session holds appends to `inbox/<writer>` ("stop and ask the user; for a repo, `agent-worktree isolate`") unless the claude process wrote it itself (every Edit/Write passed the hook's ask) or a grant covers that hold, and to `inbox/<holder>` once per writer and unit. At most one undelivered notice per key: the daemon tracks the inbox inode, and the hook takes the file by renaming it.
- **Footprint**: ~18 MB RSS. Live on this box (2026-09-24, ~100 forks/s and ~19 close-writes/s box-wide, 2/s under `~/roost`): 0.94 s CPU per 2 min. The loop is woken by writes only and drains the connector on each wake and every 0.25 s, since waking on every fork cost 7% of a core. Synthetic (`tests/conflict-watch-daemon.sh`): 640 ms CPU for 10,000 close-writes, half inside the watched trees. The health check alerts when the service is down: nothing else would, since the hook goes quiet with it.

Tests: `tests/conflict-watch.py` (no root: units, attribution, lifecycle, git classification and check), `tests/conflict-watch-daemon.sh` (sudo: the live daemon), `tests/conflict-watch-e2e.sh` (two headless sessions, a few cents of model use), `files/hooks/conflict-watch-hook.test.sh` (the hook). The session CLI lives in its own repo, cloned at `~/roost/code/session` (its README is the ops contract; `install.sh` there owns the `~/bin/session` symlink, the settings.json hook entries and `~/roost/claude/session.conf`). The usage DATA stays under `~/roost/claude/usage/`, and the mechanism below still describes what runs — kept here because this repo still deploys the conf, the tmux hooks and the cron tick that feed it.

## Data flow

The statusline (the session clone's `statusline.sh`) is the only writer of the usage data under `~/roost/claude/usage/`: `last-status.<email>.json` (per-login rate-limit cache), `session-log.tsv` (21-column per-render samples: cost, rate-limit %s, durations, cumulative tokens, context composition, lines added/removed, model, prompt_id, account), the pane→session map for focus tracking. The hooks write `turn-log.tsv` (start/end/lifecycle events) and tmux's focus hooks write `focus-log.tsv`. Live logs keep 8 days; a daily sweep moves older lines to `usage/archive/<same-name>.tsv`, append-only, so time-tracking history is permanent while the hot files stay fast.

`session` reads those: per-session $ burn is counted from the cost samples; est % of a limit = the global %-movement observed while sampling was live, split by tracked-$ share (pre-coverage burn stays unattributed; headless `claude -p` and off-box usage are invisible and inflate shares). Everything limit-related is keyed by login (the email in the invoking `$CLAUDE_CONFIG_DIR/.claude.json`): cache read and attribution filter (sample-log column 21) alike, so concurrent accounts never mix. `session time` stays account-agnostic: active = Σ turn spans — closed turns whole, and a turn missing its end (interrupt/crash; no harness event fires on Esc) credited up to its last observed work: an intra-turn subagent/compaction/permission event or a statusline sample with API-duration growth (idle still excluded, `claude -p` covered; `cost.total_duration_ms` is session wall clock ticking through idle, verified, so it cannot give this); attended = the tmux focus log; `time --all` adds a `you` row, the union of attend spans, and there is deliberately no per-session sum (parallel sessions each count in full).

Countdowns round rather than floor and drop to h+m below a day (flooring hid up to 59m: 58m of weekly headroom printed `0d00h`). A snapshot whose `resets_at` has passed shows `~0%`: the weekly is projected forward on its fixed 7-day cadence, the 5h is not projectable (usage-anchored: it opens on the first request after an idle gap) and prints `?`; `--guard` won't pause on a stale window.

`session peers` reads Claude Code's presence registry `$CLAUDE_CONFIG_DIR/sessions/<pid>.json`: cross-session address (ListAgents name = SendMessage `to:`) ↔ session id + title; REACH `no` = registered but invisible to ListAgents until that session restarts. `session name`/`id` look up id↔title across sessions (8-day snapshots first, transcript store as the slow fallback; title→id greps GBs with a stderr warning) — with the caveat that the title→id grep still only matches auto-titles, so a session found only by a `/rename`d name needs the 8-day snapshot path.

## Addressable session names

A session's registry `name` is what ListAgents prints and what `SendMessage to:` takes, and the app derives it from the cwd (`apart-research-2a`) — it never promotes the readable title into it, because the registry write is skipped for title source `auto`. So peers are addressable only by a code the user never sees. Three things set the name instead, all writing the same field: `claude --name/-n` at launch and `/rename <name>` (alias `/name`) live, both source `user` and both surviving `--resume` via the transcript's `custom-title` entry; and a `UserPromptSubmit` hook returning `hookSpecificOutput.sessionTitle`, source `hook`, which is what `session --hook` uses to promote the auto-title once, while the name is still `derived`. `user` therefore always beats the promotion and is never reverted; rename is the way to change a name afterwards. Names are unique per live session — the app renames a latecomer itself and tells it the new address.

Titles read custom-over-auto, matching the app's own precedence (`session_title`, `title_of_file`): the auto-titler keeps appending `ai-title` after a rename, so recency would undo the rename in the TITLE column while NAME kept it. `first_title` is the promotion's separate reader — the *first* auto-title, from a `TITLE_SCAN_BYTES` (2 MB) prefix. The bound is for the ~4% of sessions that never get a title, where an unbounded scan would re-read a transcript that can reach tens of MB on every prompt; over the 1,492 titled session transcripts of Aug 2026 the entry sat p50 32 KB / p99 386 KB / max 1.4 MB in, so it has never truncated a real one.

## `session reboot` / `session resume` — surviving a reboot

The presence registry `$CLAUDE_CONFIG_DIR/sessions/*.json` is pruned at startup, so the set of sessions running before a reboot is unrecoverable afterwards and has to be captured before going down. `session reboot` writes it to `usage/resume-queue.tsv` (`sid<TAB>dir<TAB>title`, overridable via `ROOST_RESUME_QUEUE`) and reboots; the systemd user unit `roost-session-resume.service` (`WantedBy=default.target`, deployed to `~/.config/systemd/user/`) runs `session resume` at boot, which replays the queue and deletes it. `SuccessExitStatus=0 1` covers `resume`'s exit 1 for an empty queue — the normal outcome of a boot not preceded by `session reboot`. The unit depends on `loginctl enable-linger`, set by `setup/shell-config.sh`; without lingering the user manager waits for a login and nothing is restored.

`resume` consumes only the entries that actually reopened: a row whose directory has gone (a deleted worktree) or that tmux refused is written back to the queue rather than dropped, so the snapshot cannot quietly lose the one record a session has left. `resume` never falls back to a transcript scan on its own: `--scan [HOURS]` is separate and explicit, so a boot with no queue restores nothing rather than resurrecting sessions the user had closed. Both paths skip session ids that are already live, so re-running is safe.

`resume_dir` recovers a session's launch directory — transcripts live under `projects/<slug>/`, the slug being that directory with every `/` and `.` replaced by `-`, so the launch dir is the recorded `cwd` that slugs back to the transcript's own directory. A transcript entry's `cwd` is only the shell's cwd at that moment and wanders into subdirectories and worktrees; the registry's `cwd` wanders the same way, and serves as the fallback. `claude --resume <id>` resolves an id from any directory, so a wrong directory misplaces a session rather than losing it.

Windows are opened with `tmux new-window` directly rather than through the `agent` shell function, whose outside-tmux branch ends in an attach that neither a batch nor a systemd unit can perform. Each window command runs under `bash -lc` so `PATH`, `CLAUDE_CONFIG_DIR` and the rest come from `roost.sh` whatever started the tmux server — at boot that is the unit, with none of a login shell's environment.

## `session account` — multi-login, one config dir

Several subscription logins out of ONE config dir, swapped in place, so transcripts, memory, settings, MCP servers and history stay shared and `--resume` keeps working. The live login is `.credentials.json`'s `claudeAiOauth` + `.claude.json`'s `oauthAccount`; the vault `claude/accounts/<login>.json` (0600, dir 0700) holds every login seen — named by email, or `<email>+<org slug>` for a Team/Enterprise seat, since one email can carry a personal plan and a seat with separate credentials and windows (added 2026-09-15 after `/login` into Apart's Team seat overwrote the Max entry; the exact name always selects, a substring both names share is refused as ambiguous). `list` shows each login's rate-limit headroom and reset countdowns (the question you switch on; a non-live login's snapshot ages from the switch), plus Fable's own weekly cap: the statusline payload never carries it, so `list` and `use` fetch it from `GET /api/oauth/usage` (`limits[]`, the `weekly_scoped` row scoped to model `Fable`) with each vaulted login's unexpired token, never refreshing one, into `usage/fable.<login>.json`. `use <#|name|substring>` (rows numbered in name order) swaps only `claudeAiOauth`: `mcpOAuth` (Granola, DoneThat) is not account-scoped and must survive. `save`/`rm` are explicit. `/login` is not destructive: the statusline autosaves the live login whenever `.credentials.json`'s mtime moves, and vault entries are never overwritten in place (the previous copy rotates into `accounts/.history/`).

A switch reaches running sessions on their next request, no restart, no re-auth. Mechanism (read out of the 2.1.220 bundle): the token is memoized in `ms.cache`, but building an API client awaits `Dy()` → `HHg()`, which `stat`s `.credentials.json` and calls `EW()` to clear that memo when the mtime moved; on Linux the plaintext backend's `read()` is an uncached `readFileSync` (the TTL cache belongs to the macOS keychain path). Measured 2026-07-31 on a controlled session: 5h 36%/wk 66% before, and the first request after the swap reported the other account's 5h 4%/wk 100%. Two consequences: the switch is box-wide (every `claude` shares the config dir), and between requests the statusline merely repeats the last API response, so displayed %s catch up one turn later; misreading one of those stale repeats is what first made this look like it had not switched.

`--wait` (any variant) also exits within ~1s of a login switch, via an inotify watch on the config dir (15s polling without inotifywait): the wait was armed against the old login's window, so the switch is the wake-up.
