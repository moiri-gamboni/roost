# scripts/ — user CLIs

Deployed to `~/roost/claude/scripts/` and symlinked into `~/bin` by `setup/shell-config.sh`.

- `roost-apply.sh` — config deployment. Usage is in the root CLAUDE.md and `roost-apply --help`; the manifest is the list hardcoded in the script.
- `roost-net.sh` — the travel VPN (`files/travel/CLAUDE.md`, `roost-net --help`).
- `agent-worktree.sh` — composite worktrees (`agent -w`, wired as the WorktreeCreate and SessionEnd hooks) and single-repo ones (`agent-worktree isolate [path]`, which a session takes when the conflict watch stops it in a code repo; the work fast-forwards back at session end, and a tree that cannot is kept with an ntfy). Its header is the contract and `tests/agent-worktree.sh` the behaviour spec.
- `conflict-watch.py` → `~/bin/conflict-watch` — the conflict watch's daemon and CLI (section below).

## What this repo deploys for the `session` tool

The CLI, its statusline, its settings.json hook entries and the `~/bin/session` symlink come from the clone at `~/roost/code/session`, installed by its `install.sh` (README = ops contract; `session --help`). This repo deploys what feeds it on this box:

- `files/session.conf` → `~/roost/claude/session.conf` — a copy of what `install.sh` writes: the data root `~/roost/claude/usage`, the tmux main guard, the attention bridge and tail, and the primary config dir. Keep it identical to the installer's output; `roost-apply diff` shows drift.
- `files/tmux.conf` — the focus hooks (`session --focus-mark`) behind attended time.
- `files/session-focus-tick.{service,timer}` — the 10 s activity sampler. The unit comments explain why `AccuracySec=1s` and `CLAUDE_CONFIG_DIR` must stay.
- `files/roost-session-resume.service` (user unit) — runs `session resume` at boot, reopening what `session reboot` snapshotted. It needs lingering, which `setup/shell-config.sh` enables.
- `files/settings.json` — records the installer's hook and statusLine entries as they stand in the live file; the installer, not a push, is what writes them.
- `files/scheduled/session-daily-brief.sh` — reads the usage logs.

## `conflict-watch` — who is writing where

`conflict-watch.py` (`~/bin/conflict-watch`) is both the root daemon (`conflict-watch run`, `conflict-watch.service`) and the CLI the hook and the sessions call; its docstring is the contract, `files/conflict-watch.conf` the unit rules (first match wins, relative to `~/roost`; edit that file when the workspace layout changes, then restart the service). Mechanism:

- **Seeing writes.** One fanotify group (`FAN_CLASS_NOTIF`, never a permission class: a dead or stuck daemon must not block a write) with a `FAN_CLOSE_WRITE` mount mark on the mount holding `~/roost` (the btrfs root; the mirrors under `apart-research/mirrors/` are separate mounts and out of scope anyway). Event paths outside `~/roost` are dropped before any other work. A watched write is credited at once (its writer may exit any moment) but named 0.2 s later through the event's fd, which follows a rename: Edit/Write, editors and `sed -i` write a temp file and rename it over the target right after closing it, and the name at event time would be the temp one (`a.py.tmp.<pid>.<hex>`), which the git check could never match against `git status`. Deletes and renames are invisible: the dirent events are refused on a mount mark (EINVAL) and a filesystem mark on a btrfs subvolume (EXDEV), probed 2026-09-24, so `rm`/`mv` in a held unit are only caught by the hook's Bash check.
- **Crediting a write to a session.** The writer pid's parent chain is walked to the *outermost* pid in the Claude Code registry (`sessions/<pid>.json`, open = pid alive with the recorded `procStart`): the claude process itself for Edit/Write, its Bash children and anything they start otherwise, and a `claude -p` helper counts as its parent. The proc connector (netlink `CN_IDX_PROC`) supplies fork parents for writers that exit before their event is read — `sed -i` is usually reaped by then (2.8% of a probe's writes without it, 0 of 600 with it; 103 of 300 short-lived writers in `tests/conflict-watch-daemon.sh` needed it). The connector is drained before every fanotify batch, since a writer's fork is queued before its write. `CLAUDE_CODE_SESSION_ID` in the writer's environment (Claude Code sets it on the Bash tool's shell) catches detached processes that predate the daemon. Nothing found = not a session (cron, the mirrors, the user's own shell): the write holds nothing. `skip-writer` rules drop tools that rewrite many units on a session's behalf (`tasks pull`); `skip-name` drops `.git/`, caches and similar; and a repo hold counts only through a file git does not ignore (`git check-ignore`, run as the user, never as root).
- **Holds.** unit → session → {since, last write, the files}. A hold lasts while the session is open (pruned every 5 s), until a release (`conflict-watch release`, which drops a request in `requests/` for the daemon), and survives a daemon restart (`state.json` in `/run/conflict-watch`, which the daemon creates itself: a systemd `RuntimeDirectory=` would be re-owned to root at every start, locking the user-run hook out of its per-session files); it cannot survive a reboot, and neither can the sessions.
- **Notices.** A write into a unit another open session holds appends to `inbox/<writer>` ("stop and ask the user; for a repo, `agent-worktree isolate`") unless the claude process wrote it itself (every Edit/Write passed the hook's warning) or a grant (`conflict-watch allow`) covers that hold, and to `inbox/<holder>` once per writer and unit. At most one undelivered notice per key: the daemon tracks the inbox inode, and the hook takes the file by renaming it.
- **Footprint**: ~18 MB RSS. Live on this box (2026-09-24, ~100 forks/s and ~19 close-writes/s box-wide, 2/s under `~/roost`): 0.94 s CPU per 2 min. The loop is woken by writes only and drains the connector on each wake and every 0.25 s, since waking on every fork cost 7% of a core. Synthetic (`tests/conflict-watch-daemon.sh`): 640 ms CPU for 10,000 close-writes, half inside the watched trees. The health check alerts when the service is down: nothing else would, since the hook goes quiet with it.

Tests: `tests/conflict-watch.py` (no root: units, attribution, lifecycle, git classification and check), `tests/conflict-watch-daemon.sh` (sudo: the live daemon), `tests/conflict-watch-e2e.sh` (two headless sessions, a few cents of model use), `files/hooks/conflict-watch-hook.test.sh` (the hook).
