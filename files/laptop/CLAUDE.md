# laptop/ — runs on the laptop, not the server

Each component has a self-contained `install-*.sh` that reads `.env` and does install + unit rendering + enable in one step. Script headers carry the operational detail; this is the map plus what the headers don't say.

- **`guest-bootstrap.sh`** — one-shot provisioning of a guest device for an isolated Claude Code session (academic-research kit: Chrome, Zotero, Claude Desktop on macOS, gdoc, fnm/Node, uv, Go, agent-browser, html2markdown, mmdc, showboat, pandoc, poppler, plus the credential-free skills html2markdown/havelock-api/humanizer/zotero). Public tools only: no roost credentials, MCP servers or tailnet; auth is a manual `/login` as the designated guest account (the restriction holds because switching accounts needs a fresh browser authorization); Google Docs via a separate Google account folders are shared into. Seeds `~/research` with a CLAUDE.md inlined in the script (kept if one exists) and ends by launching `claude` there with a tour prompt (`/dev/tty` rewire for `curl | bash`). Skills are the one piece fetched from the repo. Ubuntu x86_64 or macOS (bash-3.2-compatible). Rationale: `plans/isolated-secondary-session-ideation.md` (gitignored).
- **`btrfs-backup.sh`** + `btrfs-backup-helper.sh` + `roost-backup.service`/`.timer` + `ntfy-roost-backup@.service` + `install-btrfs-backup.sh` — pull-based incremental `btrfs send`/`receive` of both snapper configs (root as `snapshot-<N>`, `roost-data` as `roost-data-<N>`) into `/backup/roost/`, each with its own incremental-parent state file. The helper is the privileged receive/rename/delete primitive, locked to flat names in `/backup/roost/`. Retention, parent pinning and the SSH-key arrangement are in the script header. The send stream carries `@rootfs` only: the nested subvolumes `setup/snapper.sh` keeps for caches and toolchains arrive as empty directories. Daily timer (`RandomizedDelaySec=1h`, `Persistent=true`); run `roost-backup` in a terminal for a progress meter. Recovery procedure: `plans/laptop-backup-recovery.md`.
- **`sp-sync.sh`** + `sp-sync@.service` + `sp-sync.path` + `sp-sync.timer` + `ntfy-sp-sync@.service` + `install-sp-sync.sh` — SuperProductivity to the server's time-tracking log, so the 07:00 planning session has yesterday's real hours with the laptop closed. Each run extracts the whole covered history into the laptop archive (`~/.local/share/sp-archive`, superproductivity-extract's `--archive`), renders one export folder per day from it (`python -m sp.days`) and pushes them, plus `sync.json`, to `workspace/timetracking/sp/` on the server; the full archive follows hourly. The push key `~/.ssh/sp-sync` is passphrase-less and confined server-side to `rrsync -wo` on that one directory from this laptop's tailnet addresses; the script sets `ControlPath=none` and `ClearAllForwardings=yes`, because riding the shared `Host roost` connection would push with the full-access key. Triggers: `sp-sync.path` on each new SP backup (about every 5 minutes while SP runs, none while it is closed) and a 15-minute timer, both no-ops when SP's newest backup and op log are what the last push sent. No shutdown hook: the lid powers the laptop off, but SP writes its data only every 5 minutes, so syncing on its writes already leaves the server at most one write behind. Alerts (ntfy through `OnFailure=`) only on the third failed push in a row, then at most every 6 hours, or on a day the renderer refuses. The path unit watches the resolved snap revision, so rerun the installer after a snap refresh. Design: `plans/sp-timetracking-sync.md` (gitignored).
- **`drop-watch.sh`** + `drop-watch.service` + `install-drop-watch.sh` — inotifywait watcher auto-rsyncing `~/drop/` to the server's `~/roost/drop/` (served by dufs). A systemd *user* service so it has the user's SSH keys.
- **`install-discord-links.sh`** — writes `~/.local/share/applications/discord-links.desktop` (`discord --url -- %u`) and makes it the `x-scheme-handler/discord` default, so the attention queue's `discord://-/channels/…` links open the desktop app. No `.env`, no units. Tested by hand on the laptop 2026-10-12: a channel link opened the app on that channel.
- **`clip-receive.socket`** + `clip-receive@.service` + `install-clip-receive.sh` — the laptop end of the server's `clip` (`files/scripts/clip.sh`), reached through the SSH forwards (README, Laptop tools); mechanism in the installer header. Tested on the laptop 2026-10-13: a `clip` fired while VS Code was unfocused pasted in another window.
- **`clip-image-serve.sh`** + `clip-image.socket` + `clip-image@.service` + `install-clip-image.sh` — the laptop end of the server's xclip stand-in (`files/scripts/xclip.sh`), which Claude Code's Ctrl+V runs: one request line per connection (`targets` or an `image/*` type), answered from the clipboard, never with text; with no image data, a `text/uri-list` naming one local PNG file is served as that PNG. Same tool condition and forwards as `clip-receive`; protocol in the serve script's header, `tests/xclip.sh` runs it against the stand-in.
- **`gh-ruleset-sync.sh`** + `.service`/`.timer` + `install-gh-ruleset-sync.sh` + `protect-main.ruleset.json` — periodic sync of the "Protect main" ruleset across all repos of the authenticated gh user (daily + 2h jitter, `Persistent=true`), closing the gap between `./deploy.sh` runs. The JSON is the single source of truth shared with `deploy.sh`'s initial provision.
- **`roost-net-fw.sh`** — open/close the Hetzner cloud firewall travel ports (443/tcp, 51820/tcp+udp, 8443/tcp; dual-stack). Firewall identity `${SERVER_NAME}-fw`.
- **`travel-clients.sh`** — SSHes to the server, runs `roost-net client <mode>`, prints or `--save PATH` or `--send-tailscale PEER`. No QR: the Android app's scanner expects URI profiles and rejects raw JSON.
- **`travel-test.sh`** — end-to-end checks for all paths; `--simulate-gfw` blocks UDP locally; `--tailscale-check` validates exit-node routing; includes the DNS-bootstrap regression assertion.
- **`roost-travel.sh`** + `roost-travel.service` + `install-travel.sh` — the laptop sing-box tunnel. The installer sets up sing-box, jq, cfst (CloudflareSpeedTest), a `cfst-probe` system user, the wrapper, the unit, a sudoers drop-in (`/etc/sudoers.d/roost-travel-cfst`) and fetches the config. `roost-travel {on|off|status|logs|config|ips}`; `on`/`off` toggle running and enabled state. `ips` runs cfst against CF's published prefixes from the laptop's network and pushes the top 5 IPs by latency to the server's `~/.config/roost-net/cf-preferred-ip` for Path A's urltest pool; cfst runs as `cfst-probe`, whose UID `fetch_config` injects into the rendered config's `tun.exclude_uid`, so its probes bypass the tun without the tunnel coming down. Only a brief sing-box restart at the end loads the new `path-a-ipN` outbounds.
- **`cf-ip-refresh.service`/`.timer`** + `ntfy-cf-ip-refresh@.service` + `install-cf-ip-refresh.sh` — daily background `roost-travel ips` (04:00 + 1h jitter, `Persistent=true`). Reuses the sudoers drop-in from `install-travel.sh`; the installer renders the units (NTFY_URL from the server's Tailscale IP) and enables the timer. Real failures (cfst binary, ssh push, sing-box restart) ntfy via `OnFailure=`; "no working IPs" is exit 0 (expected on hostile networks).
