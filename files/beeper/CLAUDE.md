# beeper/ — Beeper Server, its egress containment, and the attention-queue units

Beeper Server (the headless Beeper Desktop that the attention queue in `~/roost/code/attention-queue` reads over `127.0.0.1:23373`) is closed source and ships product analytics with no working opt-out, so it runs as its own system user, `beeper`, behind a default-deny egress policy. Plan and rationale: `~/roost/apart-research/plans/attention-queue.md`.

## Files

- `beeper-egress.sh` → `/usr/local/sbin/beeper-egress` (root). `up` resolves the allowlist, builds the `beeper-egress` chain in both `iptables` and `ip6tables`, and hooks it into `OUTPUT` for `--uid-owner beeper`; `ensure` re-resolves and rebuilds when the address set differs from the one last applied, or a chain, its final REJECT, or a hook is missing; `down` removes both (the user is then unfiltered). The chain is loopback ACCEPT, then TCP 443 ACCEPT per address, then LOG (`beeper-reject: `, rate-limited per destination so a telemetry burst cannot hide a needed host), then REJECT. It is replaced whole by `iptables-restore --noflush`, which commits atomically, so a refresh never passes through a state without the REJECT.
- `egress-hosts` → `/etc/beeper-egress/hosts`: the allowlist, one host per line with why.
- `beeper-egress.service` → `/etc/systemd/system/`: oneshot `up` at boot (after `network-online.target` and `ufw.service`: a ufw with `MANAGE_BUILTINS=yes` flushes the built-in chains on start; this box's has `no` and leaves them alone), `RemainAfterExit` so the server can `Requires=` it. No `ExecStop`: `beeper-egress down` stays a manual step, because a stopped unit must never mean an unfiltered user.
- `beeper-egress-ensure.service` + `.timer` → `/etc/systemd/system/`: `ensure` one minute after boot and every five minutes. Five, not one: a day of one-minute resolution of the seven hosts (`attention-queue/captures/dns-churn.tsv`, 1178 samples per host) recorded zero changes to any address set, so the timer is a self-heal bound for a flushed `OUTPUT` (a hand `iptables -F`, or another tool restoring the filter table), not a DNS refresh; the health check probes the policy on the same period and runs `ensure` itself when the probe fails.
- `beeper-server.service` → `/etc/systemd/system/`: `User=beeper`, `Requires=`/`After=beeper-egress.service`, and `ExecStartPre=+/usr/local/sbin/beeper-egress ensure` on every start including `Restart=on-failure` restarts, because `Requires=` orders the egress unit but does not re-apply its rules (measured: a restart under `Requires=` alone ran unfiltered). `NoNewPrivileges`, `ProtectHome`, `PrivateTmp`. Manifest action is `daemon-reload` only: a restart would drop the session, so restart by hand.
- `attention-bridge@.service` → `/etc/systemd/system/` (envsubst `USERNAME`, `HOME_DIR`): one self-hosted bridge per instance, `bbctl run --type %i --custom-startup-command ~/.local/share/bbctl/built/mautrix-%i sh-%i` as the user. Instances: `slack`, `discord` (the legacy mautrix-discord, linked against libolm; only the Apart server is bridged), `email` (the matrimail fork for the Apart Gmail mailbox, run through the drop-in `attention-bridge@email.service.d/matrimail.conf` as bbctl type `bridgev2` with `--no-override-config`, because bbctl's generic template has no `gmail_oauth` section and would drop the OAuth client on every start; its passphrase is `/etc/attention-queue/matrimail.env`, root 0600, outside the bridge directory). Independent of `beeper-server` (the bridge talks to `matrix.beeper.com` over a websocket). `Restart=on-failure`, and bbctl forwards SIGTERM to the bridge. Manifest action `daemon-reload` only.

## State and inspection

- `/var/lib/beeper-egress/addresses`: the union of every address ever resolved for the hosts still listed (`<address> <host>`), so a DNS rotation can add addresses but never strand the server; removing a host from the list drops its addresses on the next `ensure`. `addresses.applied` is the set last applied in both families, written only after both succeed, so a failed apply is retried on the next run. Runs take a lock (`/run/beeper-egress.lock`), so the timer and a server start never interleave.
- Rejected traffic: `sudo journalctl -k | grep 'beeper-reject: '` (the kernel journal needs root). A reject to a known telemetry host is the policy working; a reject to anything else means Beeper needs a host the list lacks.
- The chain: `sudo iptables -S beeper-egress`, `sudo ip6tables -S beeper-egress`.
- The chain is the only per-uid rule this policy puts in `OUTPUT` (`-j beeper-egress`, not `-j REJECT`), and the travel VPN's kill-switch checks match xray's own uid, so neither policy's checks can pass on the other's rules.

## Paths

- `/opt/beeper-server/<version>/beeper-server` with `current` → the running version, plus the vendor tarball beside it for rollback; the feed publishes a sha512 to check a download against (`https://api.beeper.com/desktop/update-feed.json?bundleID=com.automattic.beeper.server&platform=linux&channel=stable&arch=x64`).
- `/var/lib/beeper-server` (0700 `beeper`): the user's home; `.cache/BeeperServer/` is where the binary unpacks itself, `data/` is `--data-dir` (message store, logs, `config.json` with `sentry_disabled`).
- `~/.local/share/bbctl/built/`: `bbctl` and the bridges, built here from pinned release tags rather than downloaded (bbctl's own download path has no checksum). Bridges build with the pure-Go crypto backend, `./build.sh -tags goolm -o <path>` in a checkout of the tag, and run through `bbctl run --custom-startup-command <path> sh-<type>`; `~/.local/bin/bbctl` and the unversioned bridge names are symlinks to the current build.
- `/opt/beeper-server` and `/var/lib/beeper-server`, plus the bridges' `~/.local/share/bbctl` and the queue's `~/.local/state/attention-queue`, are nested btrfs subvolumes: decrypted message text stays out of snapper snapshots and the off-site backup.

## Operations

- `setup/attention-queue.sh` (run by `deploy.sh`) is what a rebuilt box needs before the logins: the `beeper` user, the four nested subvolumes (refuses an existing plain directory rather than converting it), Beeper Server pinned to `BEEPER_SERVER_VERSION` and checked against the feed's base64 sha512 before unpacking, `data/config.json`, the egress script and allowlist, the five unit files, and the enables that `roost-apply push` never does. Egress and its timer are started; the server and the bridge are enabled only, because both need a login first (they start at the next boot regardless).
- The pass runs every quarter hour from `files/private/cron-mirrors` (`flock -n`, log `~/.local/state/attention-queue/pass.log`).
- The dead-man is `files/private/health-check-attention-queue.sh`, sourced by the private app checks every five minutes: `/v1/info` answers; `/v1/accounts` lists at least one account and every one is `connected` (the self-hosted bridge shows up there, not in `/v1/bridges`; `/v1/app/setup` is not read because it can sit at `initializing` after a restart while everything works); `state.json`'s `last_run.at` under 45 minutes old, `last_run.alarm` null and `last_run.errors` empty (the pass sends no alarm of its own, so this is the only listener); the four units active and enabled; both `OUTPUT` hooks and both final `REJECT`s present plus the two-sided probe as `beeper` (matrix.beeper.com connects over v4 and v6, rudderstack is refused), with one `ensure` before alarming; and rejects since the last check to any destination other than the three telemetry hosts, with an unreadable kernel journal or a crashed classifier alarming rather than reading as "no rejects". Every failure line reads the same on each run for the same fault (ages, counts, epochs and exit codes go to the log only), because the health check's hourly cooldown is keyed on the failure text. Tested by `files/private/tests/attention-queue-health.sh` on fixtures cut from live captures.
- Credentials (setup token, bbctl login, Slack session, recovery key), rollback, updates and the firewall-flush caveat: `docs/runbooks/attention-queue.md`.
